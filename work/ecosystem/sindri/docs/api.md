# HTTP API

Source: the routes registered by `buildServer` (`apps/server/src/app.ts` and `apps/server/src/routes/`). The list below was taken from Fastify's `printRoutes()` on the built server, so every route the server serves is here.

## Conventions

* Base `http://127.0.0.1:7800`. Loopback only unless `SINDRI_ALLOW_REMOTE=1` with TLS.
* Every `/v1/*` route except `GET /v1/health` needs `Authorization: Bearer <token>` (`sindri token show`).
* `POST`, `PUT` and `DELETE` need an `Idempotency-Key` header (422 `idempotency_key_required` otherwise), except `POST /v1/approval-session`, whose response holds a secret and is never stored, and the read-only `POST /v1/guide/ask`. The same key with the same request replays the stored response with `Idempotency-Replayed: true`; the same key with a different request is 409 `idempotency_mismatch`; a request still running is 409 `idempotency_in_progress`; 5xx outcomes release the key.
* Approvals (spec approve, plan approve, PR request, accepting or rejecting a research document, posting a PR review to GitHub) also need `X-Sindri-Approval: <approval secret>` from `POST /v1/approval-session`, which trades the pairing code printed by `sindri start` for a secret. Without it: 403 `approval_required`.
* A request with an `Origin` outside the allowlist gets 403 `origin_forbidden`; a non loopback `Host` gets 403 `host_forbidden`.
* Errors use `{ "error": { "code", "message", "details?" } }`. JSON responses (except settings) are display sanitized server side: markup is stripped and strings are cut at 64 KB. The one exception inside a response is the `patch` field of `GET /v1/deliveries/:id/local`, which is served byte for byte so it applies; render it as text.
* A failed LLM provider call is 503 `provider_unavailable` (`provider_unavailable`, `auth`, `rate_limited`) or 503 `provider_error` (`timeout`, `invalid_output`, `refused`, `api_error`). The message names the cause in brackets, and `details.reason`, when present, is the end of what the provider's CLI reported, with secrets redacted.

| Status | Codes                                                                                                         |
| ------ | ------------------------------------------------------------------------------------------------------------- |

### Work kinds

An intake's `workKind` is `change` (the default, and every intake written before work kinds), `research` or `pr_review`. The Director never changes it: when it classifies a change request as an investigation, the spec `meta` carries `suggestedWorkKind: "research"` for the operator to act on.

* `notes` (at most 8 KB) and `skillIds` (at most 20 library skills) apply to every kind.
* `research` (research only): `{sources?: {code?, feedbackGraph?, web?}, factCheck?}`. Unset fields default to code and lessons on, web off, fact-check on. At least one source must be on.
* A research plan is one `investigator` task `research` (a read-only document task, with web access only when `web` is on), followed by a `reviewer` task `fact-check` unless `factCheck` is off.
* A PR review plan is one `reviewer` task `pr-review`, plus a `security` task `security-review` when a changed path touches authentication, sessions, tokens, secrets, permissions or other security words. Both are read-only document tasks without network. A `pr_review` intake comes only from a GitHub pull request URL (a manual one is 422).
* Plans carry `work: {kind, research?, prReview?}` and `guidance`, the operator guidance every brief gets: the project's default skills plus the request's own (each with its sha256), the project notes and the request notes. The rendered block is at most 48 KB; a skill that does not fit is listed as omitted, never cut.

### Research deliveries

A research task writes `.mimir/artifacts/research.md` (sections Answer, Findings, Open questions, Sources) and `sources.json` (`[{id, kind: file|url|lesson, ref, title?}]`). There is no Brokkr verification. The research gates read only the artifacts Mimir recorded:

* `research-document`: the document exists with the four sections;
* `research-sources`: `sources.json` parses, with unique ids, and lists at least one source (`no_sources`);
* `research-citations`: the document cites at least once (`no_citations`) and every citation resolves to a source. Source-list sections (`Sources`, `References`, `Bibliography`, `Citations`, `Works cited`, at any heading level, up to the next heading of that level or higher) are not searched for citations. A citation is `[1]`, `[1, 2]` or a run such as `[1][3]`, outside code, not right after a word character, `]` or `)` (so `items[0]` is not one), and not a `[n](url)` link. Ranges such as `[1-3]` fail with `citation_range_unsupported`;
* `research-file-sources`: each `path:line` or `path:start-end` exists at the task's base commit, with the range inside the file (`file_not_found`, `line_range_invalid`). When the file cannot be checked the reason is `file_unverifiable:<id>:<why>`, where `<why>` is `no_base_commit`, `repo_unavailable`, `commit_invalid`, `commit_unresolvable` or `git_failed`;
* `research-source-policy`: URLs are http(s) and only with web on; lesson sources only with lessons on, and only the lessons the task was given; file sources only with code on.

The delivery report (`GET /v1/deliveries/:id`) then has `workKind: "research"`, an empty `summary`, `guidance` (skill names and digests, both notes and their digests) and `research`: `{question, sourcesAllowed, planTaskId, document: {markdown, artifactId, taskId} | null, sources: [{id, kind, ref, title?, private?}], sourcesArtifactId, containsPrivateSources, gate: {passed, failures}, factCheck: {planTaskId, verdict, findings, reviewArtifactId, gatePassed} | null, decision: {decision, actor, reason, decidedAt} | null}`. Lesson sources are `private: true`. A research delivery ends with accept or reject, never a PR.

The report reads each task's artifacts from its whole lineage (its Mimir task, then the repair tasks the gates created), latest file first, as the gates do; `document.taskId` and the PR review's `reviews[].taskId` name the Mimir task whose file was read. A repair task keeps the mode of the task it repairs (a read-only document task stays one) and carries the original brief after the gate failures. When the stored plan cannot give that brief (it no longer validates as a plan), the gate escalates to a human with `repair_contract_unavailable` instead of creating the repair. A fact-check reads its research task's files from Mimir's input folder for that task (`.mimir/inputs/<slug of its title>/`); a revision of a research plan cannot rename or remove the investigator task.

### PR reviews

**Import.** `POST /v1/intakes/import` with `https://github.com/<owner>/<repo>/pull/<n>` (other hosts and paths are refused) reads the PR with the operator's own `gh` (`gh pr view --json ...`, and the changed files from `gh api repos/<o>/<r>/pulls/<n>/files --paginate`, since `gh pr view` lists only 100; hardened environment, timeout and size cap; Sindri stores no GitHub token). GitHub lists at most 3000 changed files: the rest are counted as `filesOmitted` in the plan, and the brief says so. The intake is `source: "github"`, `workKind: "pr_review"` (another `workKind` is 422), and its view has `pullRequest: {owner, repo, number, url, author, state, baseRef, baseSha, headRef, headSha, isCrossRepository, additions, deletions, changedFiles}`. Title and body are untrusted: capped, secrets redacted, shown only as display text. Without `projectId`, the one registered project whose `git remote -v` (read under the hardened git config) lists that repository is used; none or several answer 422 `project_required` with `details: {repo, candidates:[{id, name}]}`. Importing the same URL again refreshes the stored PR (new head, title, files) and answers 200. Refused in local-only mode (503 `local_only`) and when `settings.connectors.github.enabled` is false (422 `no_connector`).

**Run.** The plan pins `work.prReview` (owner, repo, number, title, body, base and head SHAs, changed paths). `POST /v1/executions` runs exactly the approved plan's PR facts and text. When the intake was re-imported with a new head since, it answers 409 `pr_changed_since_plan` (`details: {planHead, currentHead}`): propose and approve a new plan from the spec, which picks up the new head. Otherwise it prepares Sindri's own clone `<dataDir>/review-mirrors/<projectId>` (`git clone --no-checkout --filter=blob:none https://github.com/<owner>/<repo>.git`, then the base and head commits, falling back to `refs/pull/<n>/head`; credentials come from `gh auth git-credential`), registers it once as the Mimir project `review: <owner>/<repo>` (hidden in Sindri's `review_mirrors` table, with the execution profile of the project it mirrors) and starts the mission at the head commit. The mirror's own git config uses only `gh auth git-credential` for github.com (inherited helpers reset), so later blob fetches of the partial clone work for private repositories; hooks, fsmonitor and submodules are off. Before the run starts, Sindri itself fetches both sides of every changed file (`git diff base...head`) and every file at the head (the checkout), then checks without fetching that none is missing (502 `mirror_failed`, `blobs_missing` otherwise). So a reviewer can read every changed file on both sides and every file at the head; unchanged files at the base may be unavailable offline. Each PR's commits are kept under `refs/sindri/pr/<n>/`; refs of PRs fetched over 30 days ago, or beyond the 20 most recent, are deleted on the next fetch. Nothing is written to the operator's checkout. 502 `mirror_failed` (`details.reason`: `clone_failed`, `fetch_failed`, `commit_missing`, `blobs_missing`, `invalid_pr`, `no_data_dir`), 503 `local_only`. The brief holds the PR text as untrusted data, the operator guidance as trusted input, and no operator lessons.

**Output.** Each reviewer writes `.mimir/artifacts/review.json` and `review.md`. `review.json` extends the code-review file: `{verdict: "comment"|"approve"|"request_changes", summary, findings: [{id, severity: critical|major|minor|nit|info, category?, file?, line?, endLine?, side?: "RIGHT"|"LEFT", message, suggestion?}], acceptance: [], decisions: []}`; an older review file still parses (`blocking` reads as critical). Gates (recorded artifacts only, no Brokkr): `pr-review-schema` (`review_missing`, `not_json`, `schema:<path>`, `summary_missing`, `finding_ids_not_unique`) and `pr-review-markdown` (`markdown_missing`, `markdown_empty`).

**Report.** `GET /v1/deliveries/:id` has `workKind: "pr_review"`, an empty `summary`, `guidance` and `review`: `{pr: {owner, repo, number, url, title, baseSha, headSha, mergeBaseSha}, planTaskId, verdict, summary, markdown, reviewArtifactId, markdownArtifactId, findings, reviews: [{planTaskId, role, verdict, summary, markdown, gatePassed, taskId}], gatePassed, gateFailures, hunksAvailable, draft, posted}`. Each finding is `{id, planTaskId, severity, category?, file?, line?, endLine?, side, message, suggestion?, placement: "inline"|"general", placementNote?, included}`: `inline` when its whole line range sits inside one changed hunk of `git diff --unified=0 base...head` (read in the mirror: the change since the merge base, as GitHub shows it, so LEFT-side lines are merge-base lines; `mergeBaseSha` is null when the diff could not be read) on its side, otherwise `general` with the reason (no line, outside the changed lines, file not in the PR, diff unreadable). No finding is dropped. A finding without an `id` gets `f-<10 hex>`, a hash of its task, file, line, side and message, so ids (and the draft edits keyed on them) survive reordering; repeats get `-2`, `-3`. Findings of the security reviewer have ids `security-review.<id>`.

**Draft.** `draft` is what gets posted: `{version, verdict, summary, findings, editedBy, editedAt}`. Version 0 is the agent's summary and findings with verdict `comment`. `PUT /v1/executions/:id/review` stores the next version (the agent's review stays as recorded); `suggestion: null` clears a suggestion.

**Post.** `POST /v1/executions/:id/review/post` (approval secret) checks, in order: not posted yet (409 `already_posted` with the URL; a second request while one is posting is 409 `post_in_progress`), every reviewer gate passed (409 `gates_not_passed`), the leak check (422 `post_blocked`), local-only off, and the PR head unchanged (`gh pr view`; 409 `pr_head_moved`: re-import and run the review again). It then sends `gh api -X POST repos/<o>/<r>/pulls/<n>/reviews --input -` with `{commit_id: headSha, event: COMMENT|APPROVE|REQUEST_CHANGES, body, comments}` on stdin: `body` is the summary followed by the included general findings, `comments` the included inline findings (`path`, `line`, `side`, and `start_line`/`start_side` for a range). The body ends with a hidden marker `<!-- viking-review:<executionId>:<payload sha256, first 16> -->` (shown in the preview; not part of the leak check). Before posting, and again when the POST fails or times out, the PR's reviews are listed (`gh api .../reviews --paginate`, GET): a review carrying this execution's marker is recorded instead of posting again. Every POST is first recorded in `review_post_attempts` (draft version, payload hash). The posted review (`reviewId`, `htmlUrl`, `draftVersion`, `commitId`, `payloadSha256` of the payload without the marker, `actor`, `recovered`) is stored once per execution in `review_posts`. A review found by its marker is recorded with the attempt whose hash its marker carries (so with the draft version that was really sent); one that matches no attempt is recorded with `draftVersion: null`, the marker's hash and `recovered: true`. Draft edits are refused (409 `post_in_progress`) while a post runs. The leak check refuses any posted text that names private local tooling (its name, its tool prefixes or its local port), cites a `lesson:<id>`, or matches the secret scanners; `details` name the `rule` (`private_tooling`, `lesson_reference`, `secret:<pattern>`), the `findingId` (null for the summary) and the `field`. Excluding or rewording the finding clears it.

### How a run ends

An execution is final in `verified_pending_review`, `cancelled` or `failed`.

* `failed`: Mimir ended the mission as failed (`mission.failed`). Nothing more can be decided on it.
* `cancelled`: an escalation was answered with `abort`, the mission was cancelled in Mimir, or the run was cancelled through `POST /v1/executions/:id/cancel`. That route works in every open status (running, awaiting a human, blocked, replan requested). It cancels the Mimir mission (a mission that has already ended counts as stopped), closes open inbox items, marks pending approvals `expired`, and stores an `execution_cancelled` event with the actor and reason. The bearer token is enough, as for `abort`.
* `replan_requested` is not final. The run continues when a revised plan of the same plan lineage (`POST /v1/plans/:id/revise`, then approve) is executed: `POST /v1/executions` for that plan cancels the old mission and closes the old execution as `cancelled`, with the reason `superseded by revised plan <id> (version <n>)` in its `execution_cancelled` event. A plan proposed anew for the spec is a different lineage and leaves the old run open; cancel that one explicitly.

## Guide

The read-only Guide answers an operator's question from the factory docs (`BuildServerOptions.docs`, a `DocsSource`; without it the answer says the docs are not installed) and a redacted snapshot of the factory state: per project, counts by status of specs, plans, runs and deliveries, waiting approval requests, pending steward decisions, open escalations and budget blocks, with titles only. Ticket titles and labels go to the provider in data blocks, with injected instructions removed. It has no tools and calls no mutating service; links point at the screen where the operator acts.

| Method | Path            | Body or query                                                                                                   | Response                                                                                                                                                       |
| ------ | --------------- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/guide/ask` | `{question (1-2000 chars), context?:{app:"sindri"\|"heimdall"\|"mimir"\|"skidbladnir", screen?, projectId?}}`; no `Idempotency-Key`; optional `X-Guide-Client` (1-128 chars of `A-Za-z0-9_-`) gives each client behind a shared token its own rate-limit bucket | `{answer (markdown), links:[{label, href}], sources}`. `href` is a Sindri web hash route (`#/reviews?project=…&execution=…`), only to real views and ids in the snapshot; `sources` are `docs:<slug>`, `glossary:<term>`, `state`. 422 `validation_failed` (bad body or `X-Guide-Client`; neither counts against the limit); 429 `rate_limited` (30 per minute per token and `X-Guide-Client`, with `Retry-After`); 503 `provider_unavailable` / `provider_error` |
